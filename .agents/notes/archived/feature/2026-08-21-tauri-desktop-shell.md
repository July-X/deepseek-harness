# Agent Note: Tauri desktop shell for kernel management

Status: implemented
Archived: 2026-08-28

English | [中文](2026-08-21-tauri-desktop-shell.zh.md)

## Problem

DeepSeek Harness is consumed today through the browser UI started by `npx @deepseek-ai/dsh web` (or `pnpm dsh web`) on `http://127.0.0.1:3080`. Users asked for a desktop shell that (1) opens the harness freely on the desktop, (2) offers a kernel-update menu that follows the official `deepseek-ai/deepseek-harness` release tags to install and switch kernel versions in place, and (3) is published through GitHub Actions for Intel macOS and Windows. The official GitHub releases only attach source archives; the actual kernel is distributed as the `@deepseek-ai/dsh` npm package (with its dozens of `@deepseek-ai/dsh-*` dependencies), published under the same version as the `dsh-v<semver>` tag. A desktop consumer therefore cannot fetch "the kernel" from a release asset — it must install the npm package pinned to the tag's version.

## Decision

**The shell is a standalone `desktop/` tree that stays outside the pnpm workspace.** It never enters `pnpm-workspace.yaml`, so the upstream lockfile, lint/hygiene/release sequences, and pack gates do not touch it and it cannot break their invariants. It is a separate deliverable with its own `package.json` (`@tauri-apps/cli` only) and its own Rust crate.

**Tauri v2 hosts three windows.** The main window loads zero-build static `ui/` assets (local management panel: status, update menu, settings, logs, and the「打开官方对话」button). Two on-demand windows are created by the user clicking buttons in the panel: `harness` is a `WebviewWindow` that loads `http://127.0.0.1:<port>` — the `dsh web` server — and `official-chat` is a bare `Window` hosting a local tab-strip WebView plus one remote content WebView per official-chat tab, including `https://chat.deepseek.com`. The official-chat window is visible before child frames are registered; after all child views are registered, a second main-thread pass reapplies bounds once AppKit has completed the display layout. Repeat clicks on either button reuse the existing window via `get_webview_window` + `set_focus`. The UI builds with Vite to `ui/dist`, which `frontendDist` serves; `withGlobalTauri` exposes the `window.__TAURI__.core` bridge for the panel's plain JS.

**The official-chat window presents an honest desktop-Edge identity so chat.deepseek.com’s environment check treats it as a regular desktop browser.** It is a bare `Window`; its local strip WebView starts with a static tab list and reconciles it with `official_chat_tabs` when IPC succeeds, so a stale or restricted build does not render an empty strip. `official-chat-strip.json` targets the exact `official-chat-strip` WebView label. `relayout_official_chat` applies each child frame with one `set_bounds` call because Wry's macOS bounds readback uses the opposite y origin; `open_official_chat` uses the requested 1366x768 logical size when AppKit reports a provisional client size, then queues an idempotent show message and a relayout task after all child views are registered so the task runs after the display pass, and its listener also relayouts on `Focused(true)`. `open_official_chat` does not override the user agent: the WebView2 engine IS a genuine desktop Edge build, and an overridden UA claiming Chrome would contradict the un-overridable `Sec-CH-UA` client hints and native `navigator.userAgentData` — that cross-layer mismatch is exactly what environment probes flag. On every platform the builder calls `.additional_browser_args(OFFICIAL_CHAT_BROWSER_ARGS)` (only the WebView2 backend consumes browser args): it restates wry’s default disable-list (`msWebOOUI`, `msPdfOOUI`, `msSmartScreenProtection` — custom args replace the defaults) and adds `AutomationControlled`, `TranslateUI`, `InterestFeedContentSuggestions`, and `--disable-blink-features=AutomationControlled`. Custom args require a dedicated user-data folder — WebView2 demands identical environment options per folder, and the panel/harness windows already run default options on the default folder — so the builder pins `.data_directory` to `<data_dir>/webview-official-chat`; the dedicated folder doubles as a persistent profile, so the DeepSeek login survives shell restarts while staying isolated from the panel and harness windows. Tauri 2.11 builder ordering stays load-bearing: attribute calls come before every `initialization_script` and before `.build()`. Remote content WebViews receive `titlebar-pulse.js` then `chat-fingerprint.js`; the local strip receives only `pullstring-launcher.js`, preserving its Tauri bridge for tab commands. The command is `async` and reports the `Result<(), String>` builder outcome back over a `std::sync::mpsc::channel` awaited via `tauri::async_runtime::spawn_blocking`, so the IPC caller only resolves `Ok(())` after the window is actually registered. The panel reads `StatusView.official_chat_open` on every 2.5s poll and toggles the same button between "打开官方对话" and "关闭官方对话"; clicking the open-state button invokes the new `close_official_chat` command (which destroys the registered webview or surfaces a "官方对话窗口未打开" error).

**Kernel versions are npm installs pinned under the app data dir.** `fetch_releases` reads the official release list via the GitHub REST API and falls back to the releases Atom feed when the API is rate-limited (the tags are identical; the fallback loses only the prerelease flag). Installing a version runs `npm install --prefix <app_data>/kernels/<version> @deepseek-ai/dsh@<version>`; the active version is a plain text file `<app_data>/active.txt`. First install auto-activates and auto-starts; later installs leave the active version alone. The update menu therefore "replaces the kernel" by pinning another version and switching the active pointer, never by patching an existing install.

**Node comes from the environment, configurable.** The shell resolves `node` from settings, then the PATH, then well-known locations, and validates against the dsh engine range (`^22.19 || >=24`); npm resolves from settings, then the folder next to `node`, then the PATH. This keeps the POC free of a bundled Node sidecar.

**Publishing is a dedicated workflow.** `.github/workflows/desktop-release.yml` builds with `tauri-apps/tauri-action` on `macos-13` (Intel macOS, `.dmg`) and `windows-latest` (`.exe`/NSIS), triggered by a `desktop-v*` tag or manual dispatch, emitting a draft release so a human publishes.

**The workbench and the official chat get the same chrome-row pulse and pull-string launcher, with per-origin colors.** `titlebar-pulse.js` and `pullstring-launcher.js` are injected into the `harness` WebviewWindow; official-chat content WebViews receive `titlebar-pulse.js` and `chat-fingerprint.js`; the local tab-strip WebView receives `pullstring-launcher.js` and retains the Tauri bridge for tab commands. The scripts pick their palette and offsets from the current page: `chat.deepseek.com` uses DeepSeek official blue `#4D6BFE` (rgb 77,107,254) and the strip lamp is anchored at `right:12px`; the dsh web workbench uses Gitea green `#609926` and anchors its lamp at `left:212px` next to the sidebar-collapse button. The titlebar script appends the half-cycle `data-titlebar-pulse="2"` node when a remote page does not provide one. Both scripts have `if (window.top !== window.self) return` top-frame guards so nested frames do not create duplicate chrome. Each remote origin has a dedicated capability file (`harness-remote.json` / `official-chat-remote.json`) granting only `allow-focus-main-shell`; URLs are pinned to exact hosts (`http://127.0.0.1:*` and `https://chat.deepseek.com/*`), with no wildcard domains. The harness window is `closable(false)` to prevent accidental session loss; the official-chat window remains closable because it does not own a kernel session.

**The kernel child is reaped on exit.** On Unix it starts in its own session (`setsid`) so stopping signals the whole process group; on Windows `taskkill /T /F` tears down the tree.

## Alternatives considered

**`apps/desktop` inside the pnpm workspace.** Rejected: the repo's package constraints, lint surface, and release/pack sequences all scan workspace members; a Rust/Tauri deliverable there would drag foreign tooling into the upstream gates and its `package.json` would have to satisfy the workspace invariants. The standalone `desktop/` tree is the smallest-blast-radius home for the fork's own product.

**Bundling a Node sidecar for out-of-the-box operation.** Rejected for the POC: each platform needs its own Node binary (+40 MB per target), the shell must self-bootstrap it, and the local environment cannot verify a Rust build at all. Environment-node detection with a configurable path is the reversible default; a sidecar slot is documented as follow-up.

**Fetching the kernel as source tarballs from GitHub releases.** Rejected: a desktop app cannot run `pnpm install` + a full harness build on the user's machine; the publish contract is npm anyway, one version per `dsh-v*` tag.

## Consequences

The shell hosts one main WebView plus child WebViews in two on-demand windows: the local static management panel is the only window that exists on startup and the single place that manages kernels; `harness` (a `WebviewWindow`) carries `dsh web`; `official-chat` (a bare `Window`) carries a tab strip plus one content `Webview` per `OFFICIAL_CHAT_TABS` entry: the DeepSeek chat, Qianwen, and MiniMax. The `official-chat` window does not own a kernel session, so the OS chrome close button keeps working; the `harness` window is `closable(false)` to prevent accidental session loss, and the panel reopens either on demand via `get_window` / `get_webview_window` + `set_focus`. Kernel data (sessions, settings, profiles) stays in dsh's own `~/.dsh` home; only the shell's metadata (installed versions, active pointer, settings, logs) lives under the app data directory. The GitHub REST fallback to Atom is observable only as a warning in the update menu. Installers are unsigned, so Windows SmartScreen and macOS Gatekeeper show warnings until code signing is added. The panel auto-recovers a stale state by probing the port on every status refresh.

Closing the management panel cascade-closes the `official-chat` window (and its tab webviews) on every real exit: it is a transient panel-driven window that does not own its own lifecycle, so the `RunEvent::Exit` handler destroys it via `get_window("official-chat").destroy()`; destroying the bare window tears down its child webviews while the persistent data store survives. The `WindowEvent::CloseRequested` interceptor parks the close and asks for confirmation when the kernel is running or the chat window is open, destroying nothing until exit — a cancelled prompt restores the prior state with every window intact. The `harness` workbench window is intentionally NOT cascaded — its lifecycle is tied to the kernel child through `stop_kernel`, and there is no documented signal tying it to the management panel, so closing the panel does not (yet) close the workbench.

## Testing

Config JSON files are validated with `python3 -m json.tool`. The app icon is the official DeepSeek favicon (`desktop/assets/whale-favicon.svg`, black body, captured from `https://fe-static.deepseek.com/platform/favicon.svg`) with a red eye added as a vector circle (`desktop/assets/whale-icon.svg`); the bitmap set in `src-tauri/icons/` is down-sampled from a 512px browser rasterization of that SVG (`desktop/assets/whale-icon-512.png`) and verified with `file`. The release list for the update menu now comes from the npm registry (`https://registry.npmjs.org/@deepseek-ai/dsh`, the same package the user lands on via `https://www.npmjs.com/package/@deepseek-ai/dsh`); `fetch_npm` parses `versions` + `dist-tags` so prerelease flags and timestamps are accurate. GitHub Releases (`fetch_api`) and its public Atom feed (`fetch_atom`) are kept strictly as fallbacks when the registry is unreachable; the UI surfaces a `warning` field on the result so users can tell which source answered. Four Tauri 2.x startup footguns are explicitly avoided by the current code: `WebviewWindowBuilder` is created on a fresh OS thread from `open_harness` so a synchronous command does not deadlock the main thread on Windows; `macOS.infoPlist.NSAppTransportSecurity` is omitted so WKWebView uses the platform default local-network policy; `capabilities/default.json` does not hardcode a `$schema` path that does not exist before the first `tauri build`; and `ureq` is requested with the `rustls` feature (the 3.x feature name is `rustls`, not `tls`) so the GitHub release and Atom feed fetches work without a system TLS dependency. Several compile and run-time errors were fixed after the first attempt at the same code: `commands.rs::install_kernel` clones `data_dir` and `version` before moving them into the `spawn_blocking` closure so it can still use them after the join; `commands.rs` sends `String` (not `&str`) into `Channel<String>::send`; `kernel.rs::port_open` builds `SocketAddr::V4(SocketAddrV4::new(Ipv4Addr::new(127, 0, 0, 1), port))` explicitly because `(&str, u16)` does not implement `Into<SocketAddr>`; `releases.rs` uses ureq 3.x's `.header(...)` (not `.set`) and annotates every `map_err` closure parameter with the matching ureq error type; `node.rs::parse_version` pins `parse::<u32>()` on each numeric piece; `kernel.rs::start` lifts `port.to_string()` into an explicit `String` before the `cmd.arg(...)` chain; and `releases.rs::parse_atom` keeps the slice offsets against the original buffer so titles with multi-byte UTF-8 characters do not split a code point and panic in `tauri dev`. Four robustness fixes from the code review round: `run_pnpm` receives on `recv_timeout(10s)` so a silent dependency-resolution phase emits an elapsed-time heartbeat instead of looking hung; the kernel's pid is recorded in `<data_dir>/kernel.pid` at spawn and both `stop_kernel` and the `RunEvent::Exit` hook fall back to `kill_pid` (guarded by a `ps` command-line check against pid reuse) so an orphan kernel from a crashed shell run can still be reaped; `write_active` writes `active.txt.tmp` + renames, and tolerates removing a missing file, so a crash cannot truncate the active pointer; and `rotate_install_logs` keeps only the newest 9 install logs before each install. The official-chat fallback resolver is covered by `desktop/ui/test/officialChatTabs.test.js`; `npm run build:ui`, `cargo check`, and `cargo clippy --all-targets` cover the current desktop UI and Rust assembly, while the `desktop-release` workflow remains the release artifact check. The update menu's release listing is fully exercised inside the app against the live npm registry (and the GitHub fallback).
